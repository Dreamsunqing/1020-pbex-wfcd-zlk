# P3 全量静态合并实现（0.9.0）

本文保留 0.9.0 的历史实测。当前 0.10.0 已补充嵌套字段合并、技能实体及组件导航，见 [文档 24](24-嵌套合并与关系导航.md)；当前统计以最新全量验收基线为准。

本次从 0.8 的 51 实体小闭环扩展到全量静态资料，新增顶层“合并规则”。目标是让同事在离线资料上共同理清分类、字段和关系，再供仓鼠互助洞 App 试接。没有部署 uniCloud、ECS 或线上 API；邮件继续预留。

## 构建流程

1. 固定所选目录／快照上下文，读取当前保存规则；CLI 默认读取内置规则，或显式传入导出的规则文件。
2. 按分类规则扫描实体；所有入选 JSON 计算 SHA-256、解析并完整保留。内容相同的参考文件按源哈希去重。
3. 使用完整内部路径关联实体；非路径标识使用 `wf:<类别>/<原标识>`，例如 `wf:region/SolNode203`。不通过中文同名、英文相似或文件名猜测合并。
4. 按分类优先级（数字越小越优先）、来源优先级选类别；按字段优先级选值。保留所有候选、原值、指针及差异。
5. 生成标准蓝图配方、材料、成品关系；遍历所有 Plus 奖励表，再关联 Oracle 全部 JobManifest 中的奖励表引用。
6. 校验字段类型、修订源哈希、关系和输入稳定性，写暂存目录并逐文件校验后切换 current。
7. 成功切换后保留上一版；失败时 current 不变。重复构建得到同一 datasetVersion，保留原比较基线。

输入文件、规则、人工修订、输出文件及其哈希共同决定 datasetVersion。时间、机器路径不参与数据版本身份。不同目录／快照的存储上下文隔离。

## 字段与分类

当前字段合同将语义明确的标量提取到统一字段：如暴击率、倍率、能量、生命、护甲、紫卡系数、紫卡档位、段位、可交易性、包内现金／内融核心、Mod 容量与等级等。可通过规则增删受支持的标量映射，并修改中文标题、说明、单位、精度、范围与适用类别。

未建模字段进入 `attributes`，按各来源原结构保留候选；例如 WFCD `attacks` 与 Plus `behaviours` 不做攻击模式相加。全部源对象可通过源指针从 reference 还原。嵌套数组、同一字段中的不同结构仍需人工整理后再定义专用适配器；编辑一条标量规则不能自动生成复杂语义适配器。

官方 `ExportRelicArcane` 混合赋能和遗物，因此其分类优先级低于明确的 Plus／WFCD 分类，避免将赋能全部误归遗物。官方技能使用 `abilityUniqueName`／`abilityName`。Plus Systems 使用 `index`。这些差异都在分类规则中显式描述。

中文名称／描述按配置的来源顺序收集指定语言原文、语言键字典、WFCD 物品本地化。仅规范化 zh-CN／en；其余语言保留参考原文。缺名蓝图可经 resultType 派生成品名称，并明确标记派生来源。缺少翻译不凭英文猜中文。

## 配方与奖励

标准蓝图配方以 `resultType`、`ingredients[].ItemType/ItemCount`、`buildPrice`、`buildTime`、`num` 为依据。比较不同来源配方时只比较成品与材料数量，不把官方额外的 ProductCategory 当作材料差异。氏族／房间研究等非标准配方保留在 dojo 实体及参考文件，尚未转换为统一递归制作成本。

奖励关联链：

`Oracle JobManifest 任意嵌套 rewards 引用 → Plus ExportRewards 完整表路径 → 池数组 → type → 显式路径别名 → 实体 → 名称／字典`

默认仅将 `/Lotus/StoreItems/` 前缀替换为 `/Lotus/`，还可配置经过核对的 exact／prefix 别名，最长匹配只应用一次。现金与内融核心包分别使用 `bundle.credits`／`bundle.endo × itemCount`；保留原包数、原 type、转换依据与每行源指针。有效概率保持原值，不重新归一化；4,640 项只有稀有度，不推测概率。UI 显示“概率未提供”。

全部奖励表均保留，不要求必须在赏金清单中出现。`bounty-references.json` 记录六类 JobManifest 的全部已匹配引用位置。静态汇总不判断实时轮次，不把池号对应任务阶段，不预测掉落，不计算钢铁之路或额外目标加成；原 Oracle 01／02 的有效世界状态查询保持独立。

## 输出与接入

```text
manifest.json                  # 输入、输出、规则哈希、版本、质量标记
contract.json / overrides.json # 构建所用规则与人工修订
items/*.json                   # 按类别分片的统一实体
recipes.json / relations.json  # 配方和关联
reward-tables.json              # 全部原始奖励表结构化结果
bounty-references.json          # 赏金清单引用
search.zh-CN.json / images.json # 搜索和官方图片元数据索引
reports/provenance.json         # 每字段候选、采用顺序、转换及修订
reports/source-records.json     # 源记录位置与未建模字段
reports/issues.json / coverage.json
reference/<source>/<原始哈希>.json
```

完整工作包包含复核报告和所有语言，所以约 691 MiB，**不建议直接整个嵌入 App**。App 试接先取所需 items、recipes、reward-tables、relations、search；根据用户访问范围裁剪语言、类别和字段。完整溯源留给工作台／后续后台。图片仍独立配置，本地有则显示，不强求下载。

为节省重复内容，完整数据包的溯源使用 `{input: n, pointer: '...'}`。`n` 是 `manifest.inputs` 的零基下标，可还原 source、file、hash；pointer 始终针对原输入。源记录值通过 coverage.files 中同 file 的 reference 路径与 pointer 还原。工作台在请求详情时展开，跳转原文件前仍核对哈希。JSON 使用紧凑序列化；以 manifest 的字节数与哈希为准，不要自行格式化后直接替换发布文件。

## 质量与未完成项

当前产物标记 `review-required`，不是经审核的线上发布包。共有 33,040 项提示，其中 23,995 项字段差异、3,964 项缺少中文、4,686 项来源分类差异、273 项同文件重复标识、72 个待补引用、45 项配方循环、5 项无效候选值。多个提示可能属于同一实体。缺失引用显式建为 reference，循环不做递归成本计算；差异暂按规则选值。

所有差异原值均可回查。优先复核实体身份和配方循环，再处理类别、关键数值、名称。报告数量下降应来自确认规则或数据修订，不能通过隐藏提示宣称数据已正确。严格的小闭环构建仍可用 `--profile pilot` 回归验证；全量工作草稿与小闭环的拒绝策略不同。

## 命令与实现入口

```bash
npm run build:data -- --root . --out artifacts/full-export
npm run build:data -- --root . --rules /path/to/merge-rules.json --out /path/to/output
npm run build:data -- --profile pilot --root .
npm run check
npm test
node scripts/check-full-ui.mjs 'dist/mac/Source Workbench.app/Contents/MacOS/Source Workbench'
```

CLI 的 `--overrides` 可单独指定人工修订并覆盖规则文件中的 overrides；`--release`／`--store` 读取保留快照。桌面保存的规则不会隐式影响 CLI，需先导出并传 `--rules`。

实现入口：`full-inputs.mjs` 扫描与适配；`full-build.mjs` 规范化与关联；`rules.mjs` 校验及持久化；`repository.mjs` 原子构建／保留／导出；`service.mjs` 详情与溯源展开；`src/ui/rules.js` 规则编辑；`src/ui/merge.js` 全量卡片及报告分页。
