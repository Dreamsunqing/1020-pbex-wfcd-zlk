# 合并规则编辑与协作（0.9.0）

顶层“合并规则”是后续资料人员、开发和复核人员的编辑入口。当前为本地配置工作台，可导入导出并通过 Git 协作；没有多人在线账号、权限管理或实时协同服务。

## 编辑、保存与生效

1. 打开“合并规则”。默认载入应用内置规则，已有本地保存记录则载入当前版本。
2. 在表单页编辑；复杂批量调整可使用“完整 JSON”。切换页签保留草稿，JSON 页切换时先解析。
3. 点击“校验规则”。此步检查配置格式、路径、类型、重复、来源顺序和人工修订字段，**不会假装已经核对全部游戏数据**。
4. 填写修改说明，再“保存规则”。保存比较载入时 revision；被其他窗口修改后拒绝覆盖，需重新打开应用载入再处理。
5. 去“合并汇总”点击“构建全量资料”。这一步核验真实输入、修订哈希和关系；不成功则继续使用旧产物。
6. 看“问题与覆盖”“构建差异”，再检查代表实体与来源。保存规则不直接改动旧数据包。

规则存放在应用用户数据目录 `merge-rules/current.json` 与 `previous.json`。同一应用配置对所选资料目录／快照生效，不随上游同步上传。快照的历史原文件不变，构建结果记录所用规则；对历史快照使用新修订时也必须满足该历史输入的源哈希。

“载入上一版为草稿”只回填草稿；仍须保存并重建。不会在退出时自动保存草稿；切页不会清空，关闭应用前请保存或导出。

## 六个页签

| 页签 | 维护内容 | 适合人员 |
| --- | --- | --- |
| 版本与流程 | 映射版本、构建兼容标记、全局来源顺序 | 负责人、开发 |
| 分类 | 来源内文件路径、启停、结构、类别、类别优先级、分组、ID 字段、语言 | 资料人员、开发 |
| 字段映射 | 统一路径、来源键、中文标题／说明、适用类别、类型、范围、单位、精度、字段来源顺序 | 资料人员、开发 |
| 路径别名 | 完整路径／明确前缀到统一路径 | 开发、复核 |
| 人工修订 | 实体、字段、源 SHA-256、JSON 值、依据 | 复核 |
| 完整 JSON | 上述配置的完整结构及少用选项 | 开发、批量处理 |

分类支持 `map`、`array`、`group`、`nested`：

- map：根对象的键即原 ID，适合 Plus ExportWeapons 等。
- array：根数组，默认取 `uniqueName`，适合 WFCD。
- group：某个顶层数组，如官方 ExportWeapons；技能指定 `abilityUniqueName`。
- nested：扫描嵌套路径键对象及含 uniqueName 的数组对象，最多五层。非实体数组仍完整保留在 reference。

分类优先级数字越小越优先。同优先级按来源顺序和稳定的文件／指针次序选择；同文件重复 ID 保留候选并报告。文件路径相对各来源根目录，不支持绝对路径、`..` 或通配脚本。目录／快照内没有某条规则的可选文件时记录提示。Plus ExportRewards 和有效实体是全量构建的必需输入。

字段路径支持 `stats.<字段>`、`bundle.<字段>`、`custom.<字段>` 以及 masteryRank、tradable、rarity、imageName、icon。当前映射是顶层来源键到统一标量路径；不能仅靠修改 JSON 实现任意嵌套数组转换、单位推测或复杂攻击模式计算。这类工作需增加代码适配器、测试，再配置规则。

不要将 `disposition`（紫卡档位）映射为 `omegaAttenuation`（紫卡系数）；不要把攻击模式中以百分数表示的数值直接当 0～1 比例。精度只用于已经确认语义一致的数值。

## 文件交换与 Git

导出规则会打开保存对话框，可保存尚未生效的有效草稿。导入文件先做结构校验，再载入草稿，仍需保存才进入当前规则。格式如下：

```json
{
  "contract": {
    "schemaVersion": 2,
    "mappingVersion": "p3-full-1",
    "builderVersion": "2.0.0",
    "locales": ["zh-CN", "en"],
    "priority": ["official", "plus", "wfcd", "oracle"],
    "scope": {"id": "full-static", "mode": "full", "label": "全量静态资料", "maxEntities": 200000},
    "catalogs": [],
    "fields": [],
    "aliases": []
  },
  "overrides": {"version": 1, "entries": []}
}
```

这是结构示意；空 catalogs 无法通过校验，实际请从工作台导出完整文件修改。文件导入上限 2 MB。不会执行字符串函数、JS 表达式或远端脚本。

建议各同事使用自己的 Git 分支维护工作台导出的规则文件和变更说明，再由负责人汇总为单一规则文件，导入、构建、验收。不要同时覆盖同一个共享磁盘 current.json；应用的 revision 保护仅防误覆盖，不是多人协同协议。本次没有自动提交或推送 GitHub。

## 人工修订示例

```json
{
  "entityId": "/Lotus/Weapons/Example",
  "field": "name.zh-CN",
  "expectedSourceHash": "这里填详情中真实的64位源SHA256",
  "value": "经过核对的中文名",
  "reason": "核对所选版本游戏内资料；关联任务编号"
}
```

表单的“修订值 JSON”需要填写合法 JSON：字符串用双引号，数字不加引号，布尔写 true／false。hash 示例占位符不能提交。源哈希来自该实体该字段的真实候选文件，不是 datasetVersion、字典名或图片哈希。修改名称时也需要候选存在；当前不能用修订创建全新实体或凭空补一个从未存在的候选字段。

修订仅支持已建模字段、名称／描述与配方 credits／seconds／quantity；材料关系和类别应通过适配器／分类规则修正。没有匹配实体、重复修订、值越界、源哈希过期都会阻止构建。旧修订需重新核对并更新哈希，不能自动忽略校验。

## 3～4 人分工与验收

| 角色 | 建议范围 | 交付与验收 |
| --- | --- | --- |
| A：实体与翻译 | 物品、资源、蓝图、Mod、赋能；中文缺失和分类问题 | 分类／字段规则、核对样例、修改依据；完整 ID 不变 |
| B：战斗字段 | 武器、战甲、同伴、技能；数值和单位 | 字段语义表；复杂攻击模式适配器与独立例子测试 |
| C：配方与奖励 | 材料闭包、包数量、赏金清单、缺失引用、循环 | 引用修复、配方证据、概率／稀有度边界；不靠名称猜 ID |
| D：集成与复核 | 汇总规则、跑构建、审核差异、裁剪 App 包 | 固定规则文件、构建版本、验收记录、App 接入分片清单 |

只有 3 人时由 A 兼 D 的规则汇总，关键数值和配方仍让另一人交叉复核。先按一组类别完成“规则修改 → 构建 → 来源抽查 → 差异验收”，再合并下一组，避免一次几千条调整失去可审阅性。

每次交付附：规则文件、mappingVersion、输入资料版本／哈希、datasetVersion、改动说明、代表性实体 ID、剩余问题。先处理身份／关联，再处理中文和一般说明；不要用隐藏 warnings 的方法制造“零问题”。App 先试接类别分片和关系索引，等离线语义稳定再讨论 uniCloud／ECS 的版本清单及 API。
