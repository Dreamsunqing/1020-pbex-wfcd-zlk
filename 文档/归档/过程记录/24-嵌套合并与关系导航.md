# 0.10.0 嵌套合并、关系导航与技能徽章

日期：2026-10-22。接续 0.9.1。目标是把战甲技能、组件等嵌套资料纳入统一实体及字段溯源，并让关联对象可以直接浏览。

## 使用方式

打开当前资料目录，进入“合并汇总”，点击一次“构建全量资料”。旧缓存缺少新模型时会提示重新构建；安装新版应用不会自动重写已保存规则或原始 JSON。

战甲详情先展示技能、组件／制造材料、附带物品、显赫武器等关系卡。点名称进入目标物品的完整卡片，点“返回上一物品”沿浏览记录返回；“返回统一资料”回到原筛选列表。组件详情可反查其所属物品，Mod 可反查其强化对象。字段中的完整内部 ID 也能跳转。

技能名称旁的“集团卡”进入对应技能强化 Mod，武器标题旁的徽章进入兼容的武器强化 Mod；多张卡分别展示徽章，悬停显示各张 Mod 的中文名称。已明确为非集团武器强化的条目显示“强化卡”。徽章说明关联关系，不承诺集团商店当前有售。

“可移植技能”进入合并后的独立技能记录，页面标识 `ExportAbilities · 合并技能目录`。Prime 的技能行显示“同系可移植”，只说明其与普通版共用技能，不能将 Prime 当作献出材料。原始来源仍从“查看原字段”进入。

详情继续采用卡片，字段中的对象、数组可以展开。每次加载 40 个直接子项，可继续展开。列表卡片仍保持精简布局，不增加大段描述。

## 嵌套数据怎样合并

| 来源结构 | 处理 | 溯源 |
| --- | --- | --- |
| `obj.inner.a` 等普通对象 | 所有来源的键取并集，递归到叶字段，各叶独立按优先级取值 | 记录真实原文件和深层 JSON Pointer |
| 每项都有唯一完整内部 ID 的对象数组 | 按 ID 对齐，先保留优先来源顺序，再补其他来源；对象内部继续逐字段合并 | 各来源保持自己的原数组下标 |
| 无 ID 数组、混合数组、数组内重复 ID | 作为整体候选，按来源优先级选择并保留差异 | 不按下标拼接，也不按名称猜测 |
| 技能映射对象或技能对象数组 | 抽取独立 `ability` 实体，与独立技能目录中同 ID 的记录合并 | 保留技能在战甲内部的实际路径 |
| 只有 `{uniqueName,itemCount}` 的组件引用 | 建关系及数量；不伪造一个有完整属性的组件实体 | 缺少真实实体时保留待补引用 |
| 有完整内容的组件对象 | 组件自身作为候选进入同 ID 实体，归属数量留在父子关系上 | 避免把“配方需 3 个”当成组件自身属性 |

新增标准字段 `stats.activationEnergy`，取技能 `energyRequiredToActivate`；战甲 `passiveDescription` 按语言键规范为中英文。其他未设置专门业务字段的嵌套内容仍进入 `attributes`，但已经逐叶合并，不再整块挑选一个对象。

“已逐叶合并”不表示所有字段的游戏语义都已人工确认。未知业务含义保留在完整来源与待释义字段中，后续人员仍需维护中文释义和标准字段映射。

## 集合与关系映射

| 来源字段 | 统一集合 | 关系 | 补充信息 |
| --- | --- | --- | --- |
| 战甲 `abilities`；项 ID 为键、`abilityUniqueName` 或 `uniqueName` | `abilities[{itemId,slot}]` | `has-ability` | 技能序号从 1 开始 |
| `components` | `components[{itemId,count?}]` | `has-component` | 保留有效数量；未知不默认为 1 |
| WFCD 组件 `parentUniqueNames` | 反向补进父项 `components` | `has-component` | 仅补归属证据，不用父列表下标覆盖数量或顺序 |
| `additionalItems` | `additionalItems[{itemId}]` | `includes-item` | 完整 ID 关联 |
| `exalted` | `exaltedItems[{itemId}]` | `has-exalted` | 显赫武器 |
| Plus 配方 `resultType`／`ingredients` | `recipes.json` | `produces`／`requires` | 原有配方关系继续保留 |
| 本次强化适配器 | `augments[{itemId,badge}]` | `augmented-by` | 技能／武器 → Mod |
| Wiki `Subsumed` | 技能 `helminth` | `subsumed-ability` | 战甲 → 同系可移植技能；另列 `donor` |

相同 `from + kind + to` 的集合归属关系去重，保留全部来源证据。组件数量不一致会形成提示，正向集合有数量的优先候选决定数量；反向归属列表不会覆盖它。组件关系与配方材料关系分开保存，避免制造成本重复计数。

## 集团卡／强化 Mod 的证据链

读取本地 `plus-gen/extras/wiki/Mods.lua` 的 `InternalName`、`IsAbilityAugment`、`IsWeaponAugment` 和 `Description`。这是只读元数据提取，不执行 Lua；注释中的标记无效。

技能强化先以 Mod 的 Plus `compat` 和战甲完整 `parentName` 链确认所属战甲范围，再使用以下有依据的对应方式：

1. Plus Mod 的 `name` 本地化键中 `AugmentNName → Name`，与该战甲技能的语言键精确匹配。
2. 未得到唯一目标时，使用 Wiki 明确写出的 `技能英文名 Augment:`，仅在已确认战甲的技能范围内做英文全名精确匹配。
3. 仍无唯一目标时不挂徽章，写入 `reports/ability-links.json` 和问题报告。不会用模糊名称、技能下标或描述相似度兜底。

例如：

- `/Lotus/Powersuits/Runner/RunnerRushAugmentCard` 的 `compat` 对应 Gauss 父类；语言键 `RunnerRushAbilityAugment1Name` 对应 `RunnerRushAbilityName`，关联马赫冲驰。
- 热能传递 Mod 对应 Gauss 的热能抽离技能。技能名称和 Mod 名称分别使用各自的中文词条，不能互相替代。

武器强化使用同一份 Wiki 的明确武器强化标记，以及 Plus Mod 的 `compatibleItems` 或 `compat`。存在 `compatibleItems` 时优先按该列表精确匹配，否则匹配完整武器 ID／父类链。检查 `incompatibilityTags` 屏蔽项，并保守要求 Mod 的正向兼容标签全部满足。不能仅因为武器名称含 Hek 就挂上 Hek 的卡，也不能因为所有 Mod 都有 `compat` 就把普通通用 Mod 当作集团卡。

战甲被动强化不对应四个独立技能，旧版已移除技能和非武器对象也可能无法匹配；本版保留待复核，未擅自挂到某一个主动技能。

## 可移植技能与 ExportAbilities

来源为本地 `plus-gen/extras/wiki/Warframes.lua`：

`InternalName → 已合并战甲完整 ID → 自身 abilities → Subsumed 英文全名唯一精确匹配 → 技能完整 ID`。

以 Gauss 为例，快照第 1369 行 `Subsumed = "Thermal Sunder"` 对应 `/Lotus/Powersuits/Runner/Abilities/RunnerTransferAbility`。技能 `helminth` 含 `transferable`、`listedFrames`、`donorFrames`，分别表示已知可移植、快照记载的同系战甲、可献出的普通版战甲。Prime／Umbra／竞技场变体从献出列表排除。没有标记表示当前来源未确认，不代表游戏中一定不可移植。

必须区分两个目录：

| 目录 | 本地快照实际内容 | 本版处理 |
| --- | --- | --- |
| 原 Plus `ExportAbilities.json` | 77 项；主要为独立技能，不包含 Gauss 的四个技能 | 作为来源保留，不向原文件补写 |
| 原官方 `ExportWarframes_*.json` 的 `/ExportAbilities` | 各语言 13 项，不能用作完整移植技能清单 | 作为来源保留 |
| **新合并输出 `ExportAbilities.json`** | 372 个统一技能，以完整 ID 为键 | 合并独立技能和战甲内嵌技能；徽章跳转该统一实体 |
| `items/abilities.json` | 同一批技能的数组分片 | 供按类别读取；避免原来的不规则复数 `abilitys` |

源文件和哈希全部进入 manifest。Lua 溯源使用空 JSON Pointer 表示整份文本，同时保留原始行号；点击后展示目标行附近原文，能定位超过原文默认 200,000 字符限制的位置。JSON 溯源继续使用精确 JSON Pointer，跳转前校验源哈希。

两个 Wiki 元数据快照缺失时，嵌套结构和普通技能关系仍能构建，强化／移植状态记为未知并报告缺失，不从名称推测补全。导出包中的 `reference` 同样保存这两份只读文本。

## 规则与协作

“合并规则 → 嵌套与关系”可编辑集合字段、标准集合路径、关系类型、嵌套实体类别、反向父级和开关；5 条默认规则对应上表前五项。旧版已保存规则没有 `nested` 时会使用内置默认值，打开该页并保存后可显式写入规则文件。不会覆盖其他既有修改。

技能强化和移植目前是代码适配器，不提供任意脚本执行入口，也不把推测结果写回源 JSON。后续维护者优先复核 `ability-links.json` 未匹配项；要补特殊对应，应提供完整 ID 和来源证据，再增加经过审核的适配规则，不能直接按中文同名连线。

推荐分工：数据人员复核未匹配项、缺失翻译和未知字段；开发维护标准字段、适配器与 ID 引用；复核人员检查来源哈希、正反关系和构建差异。共享导出的规则 JSON，通过 Git 评审后导入、校验、保存并重新构建。

## 数据与验收

本地完整结果以 `P3全量验收基线.json`、`P3全量覆盖报告.json` 为准。本版共有 32,941 个实体、2,024 份配方、1,102 张奖励表、11,509 个奖励项。嵌套抽取涉及 308 个实体、2,037 份记录；技能总计 372 个。共 28,548 条关系，374 份输入，395 份数据文件加 manifest；规范工作包 ZIP 约 56.1 MiB。完整计数和哈希见最终基线。

技能强化关系 205 条、武器强化关系 128 条，可移植技能 66 个；8 项没有唯一关联目标，明确保留待复核。仍有 28 个缺失实体引用和 22,473 项字段差异，工作包状态为 `review-required`，不能当作已经人工审核完毕的线上资料。

自动化覆盖：逐叶冲突、有 ID 数组重排、匿名数组整组选择、源指针回查、内嵌技能去重、组件数量优先与反向证据、旧规则兼容、武器兼容标签、Prime 献出限制、Lua 注释和行号、全量真实数据，以及原有图片／奖励／规则流程。

界面验证覆盖技能与组件跳转、返回上一物品、数组展开、技能能量、集团卡跳转、可移植技能目录、Prime 同系标记、源 Lua 行定位和 1080 宽窗口。Mac x64 包需实际启动验收；Windows x64 进行 ZIP／ASAR 源码与结构校验，本机没有 Windows 实机验证条件。
