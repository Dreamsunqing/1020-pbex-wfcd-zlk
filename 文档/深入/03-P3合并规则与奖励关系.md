# P3 合并规则与奖励关系

P3 把独立来源整理成可消费、可追溯的离线数据。它既不覆盖原始 JSON，也不把所有来源拼成一个巨大对象。团队先在离线工作台确定字段和关系，再决定 App 分发接口与裁剪范围。

## 入口与配置

- 桌面：“合并规则”维护，保存后到“合并汇总”构建。
- CLI：`工具/03-合并数据.mjs` → `scripts/build-merge.mjs`。
- 内置合同：`src/data/merge-full-contract.json`，当前 schemaVersion 2，mappingVersion `p3-full-2`。
- 内置修订：`src/data/merge-overrides.json`；桌面用户规则由 `RuleStore` 保存在应用用户目录。
- CLI 默认读内置合同；要使用界面中导出的用户规则，显式传 `--rules 规则JSON路径`。界面保存规则不会悄悄改写源码合同。

## 从输入到发布

1. `full-inputs.mjs` 扫描当前目录／快照。分类合同明确来源、文件、分组、记录形态和 ID 字段；字典、参考、排除分别登记。
2. 以完整内部路径统一身份；非路径键使用 `wf:<类别>/<原标识>` 隔离，避免不同键空间碰撞。
3. `full-build.mjs` 按分类、字段优先级和修订决定采用值，保留候选、指针、哈希和差异。默认来源顺序可以被字段规则覆盖，不允许用遍历顺序裁决。
4. `nested.mjs` 将嵌套技能、组件、附带／显赫物品等按专用规则建模为实体和关系，保留数量、正向／反向关联。
5. 生成配方、奖励和引用；`ability-links.mjs` 关联技能／武器强化 Mod、移植技能及元数据证据。上游 Lua 只按专用格式读取明确字段，不执行。
6. `repository.mjs` 写暂存、验证输出字节，再切换 current；失败不替换当前版本。同一内容得到同一 datasetVersion，保留当前和上一构建。

未被规范化的复杂字段进入 attributes 或 reference，不能宣称“所有 obj 都已完全理解”。例如攻击模式、氏族非标准制作流程，仍需对应语义适配器，不能靠添加一个标量字段规则解决。

## 配方和导航

标准配方由 `resultType`、`ingredients[].ItemType/ItemCount`、费用、耗时、产量等明确字段生成。详情通过组件、技能、配方成品、材料、强化卡和来源继续导航，保持卡片式展示。

图片描述由 `service.mjs` 的 `imageDescriptors` 从实体和配方得到：蓝图带 `resultId` 与成品 imageName，交给图片层叠加。不能把“蓝图 ID 字符串去掉 Blueprint 后缀”当配方关系。

## 两套赏金奖励逻辑

### 静态 P3：保留全部表及引用

关联链为：Oracle JobManifest 的 rewards 完整路径 → Plus `ExportRewards.json[表路径]` → 池数组 → 项的 type → 显式路径别名 → 统一实体 → 名称与字典。

默认只将奖励物品 `/Lotus/StoreItems/` 前缀转为 `/Lotus/`；表路径不改。`bounty-references.json` 保留清单引用，`reward-tables.json` 保留全部奖励表，不要求必须被当前赏金选中。

概率使用有效原值；只有 rarity 时显示概率未提供，不猜测、不重新归一化。现金／内融核心包按每包数值乘原 itemCount，并保留换算依据。池下标只是源数组顺序，不能自动解释为 A/B/C 或任务阶段。

`reward-context.mjs` 为卡片提供清单、任务类别和地区等中文上下文。0.13.3 起奖励列表统一尺寸，点击进入详情后多卡一行展示奖励；缺名、缺实体、缺概率分别保留可复核状态。

### Oracle 01 / 02：回答这次查询用哪张表

`oracle-bounties.mjs` 决定任务，`oracle-data.mjs` 和 `oracle-rewards.mjs` 补充任务说明及奖励。

01 的挑战档位直接用 `ChallengeMissionDifficultyTiers[i].rewards`。02 的地区普通任务共享所属地区难度目录，用 JobDifficultyTiers 的候选表结合有效世界状态 `jobs[].rewards` 求唯一交集；唯一命中标为当前轮次已确认，单一静态表可标 fixed，其余展示候选、标 unconfirmed。

seed 决定任务推算，不直接证明奖励表轮次。过期、重叠、多个候选不能静默选第一张。静态全量汇总不会因为当前世界状态变化而删掉其他表。

## 输出分层

| 文件 | 消费用途 |
| --- | --- |
| `manifest.json` | 版本、输入／规则／输出哈希、质量与统计 |
| `contract.json`、`overrides.json` | 复现本次规则与修订 |
| `items/*.json` | 按实体类别分片 |
| `recipes.json`、`relations.json` | 制作和实体关系 |
| `reward-tables.json`、`bounty-references.json` | 奖励及清单引用 |
| `search.zh-CN.json`、`images.json` | 搜索、图片元数据；不是图片二进制 |
| `reports/provenance.json` | 字段候选、转换与采用依据 |
| `reports/source-records.json`、`reports/coverage.json` | 源记录和未建模结构的还原线索 |
| `reports/issues.json` | 缺失、冲突和待复核 |
| `reference/<source>/<hash>.json` | 完整源结构与其他语言，按哈希复用 |

紧凑溯源 `{input,pointer}` 中 input 是 manifest.inputs 的零基下标。详情请求时展开，跳原文件前还要核对哈希。不要格式化后替换带签名身份的生成文件。

完整工作包包含溯源和参考，体积较大；App 先取需要的 items、recipes、relations、rewards、search，按类别和字段裁剪。没有在本项目部署 uniCloud 或 ECS API。

## 同事怎么分工

建议 3～4 人各负责一个清楚边界：分类与字段合同、中文与字典、配方／奖励／嵌套关系、图片索引与工作台体验。先共同确认完整 ID、证据格式、缺失处理和合同版本，再分别提交规则和小样本；同一份主合同由指定集成人汇总，避免四个人互相覆盖 JSON。
