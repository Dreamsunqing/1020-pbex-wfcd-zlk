# 灵化之源与武器适配索引

更新：2026-10-24，0.16.2。玩家入口见 [玩家资料库](20-玩家资料库.md)，离线快照见 [预构建资料](21-Mod赋能卡面拼图与内置资料.md)。

## 使用方式

“资料库 → 武器”增加“武器特性”选择器，支持与装备分类、版本、段位等条件交叉筛选：

- 全部：保持原武器列表。
- 灵化武器：当前快照中有明确适配关系的武器及变体。
- 其他武器：未建立上述关系的武器；这不是“不支持灵化”的结论，自带灵化形态的武器也可能在此组。

武器列表有“可安装灵化之源”徽章。进入武器详情，首屏展示带图片和名称的灵化之源入口，后续关系区也可点击“灵化之源”卡片；从灵化之源详情可沿“适配武器”卡片返回所有适配版本。卡片使用原有中文名称、说明与本地图片，支持语言切换，不展示内部路径。世界状态中的灵化之源奖励已能进入资料库，因此也能继续进入对应武器。

本地快照关联 **45 种灵化之源、89 个武器版本**，包含有明确记录的 Prime、破坏者、集团、棱晶和 MK1 版本。例如布莱顿对应普通、Prime、破坏者、MK1 四个版本。未命名的 `BaseIncarnonUnlocker` 是基类，不参与适配统计。

## 数据与证据

Plus 的资源记录提供灵化之源身份、名称语言键和图片，但本地 `ExportResources` / `ExportRecipes` 没有直接列出安装兼容武器。因此使用 Plus 生成仓库内保存的社区 Wiki 武器元数据作精确推导，不能称为官方兼容字段。

| 文件 | 字段 | 用途 |
| --- | --- | --- |
| `世界状态上游/git/warframe-public-export-plus/ExportResources.json` | 完整资源 ID、`name`、`icon` | 灵化之源实体与本地图片身份 |
| `世界状态上游/git/warframe-public-export-plus/dict.en.json` | 资源 `name` 对应英文词条 | 去掉固定后缀 ` Incarnon Genesis` 得到明确基础名 |
| `世界状态上游/git/warframe-public-export-plus-gen/extras/wiki/Weapons/primary.lua`、`secondary.lua`、`melee.lua` | `InternalName`、`Family`、`IncarnonImage` | 完整武器 ID、明确家族和灵化形态存在证据；所在文件决定主／副／近战槽位 |
| 构建产物 `relations.json` | `kind=incarnon-adapter`、`from`、`to`、`sources`、`rule` | 武器 → 灵化之源；反向索引得到适配武器 |
| 构建产物 `reports/incarnon-links.json` | `adapters`、`weapons`、`unmatched` | 覆盖数量与无法确定的关联 |
| 构建产物 `reports/provenance.json` | `links.incarnonAdapter` | 来源文件哈希、行号／指针、字典证据和规则 |

规则同时要求：资源 ID 位于 `IncarnonAdapters/{Primary,Secondary,Melee}/`，类型为资源，英文名称以固定后缀结尾；武器元数据 `Family` 与基础名完全相等，槽位一致，`IncarnonImage` 非空；`InternalName` 指向统一数据内的真实武器。只生成唯一匹配，重复证据去重；冲突、缺实体、缺形态、缺家族或多候选都留待复核。

不按中文名、模糊名称、图片文件名或父类扩散，不把蓝图、外观、同系双持武器纳入。仅有 `Incarnon Form` 攻击或自带灵化特性不足以生成适配器关系；Phenmor、Laetum、Praedos 不会因此错误链接。

Lua 只按顶层记录与字段缩进读取，忽略注释和嵌套伪字段，从不执行代码。现有技能强化解析仍保留原默认层级，武器元数据单独指定层级。

## 维护与构建

| 代码 | 职责 |
| --- | --- |
| `src/core/merge/full-inputs.mjs` | 将三个 Wiki 武器快照作为只读元数据输入，参与来源哈希 |
| `src/core/merge/ability-links.mjs` | 可指定层级和字段白名单的 Lua 元数据读取器 |
| `src/core/merge/incarnon-links.mjs` | 唯一家族匹配、双向关系的基础边、来源证据和覆盖报告 |
| `src/core/merge/full-build.mjs` | 纳入全量合并与数据版本 |
| `src/core/player-library.mjs` | 关系索引、中文筛选、列表徽章、双向详情投影 |
| `src/ui/player-library.js` | “武器特性 → 灵化武器”选择器、首屏入口与卡片跳转 |
| `src/core/player-bundle.mjs` | 保留关系并随内置快照交付，不依赖首次启动重新构建 |

执行顺序不变：`node scripts/build-merge.mjs`，再将输出的 repository 路径传给 `node scripts/prepare-player-library.mjs <repository>`。也可使用根目录 [工具说明](../../工具/README.md) 中的构建／预构建入口。新版程序仅在本地全量构建与内置资料的 `modelingVersion` 一致时采用本地数据；旧版或试验构建不会覆盖新版内置资料。旧构建在合并汇总中仍可读取，不删除、不自动重建；需要使用本地规则时，在合并汇总重建一次。界面绑定资料版本期间保持列表与详情一致，版本变化要求重新进入资料库。

验证覆盖注释及嵌套字段、完整 ID、家族／槽位冲突、重复证据、变体、自带灵化排除、筛选交集、双向跳转、来源只读，以及真实内置快照的 45／89 统计。UI 检查同时验证武器 → 灵化之源 → 另一武器、图片加载和中英文切换。

## 0.16.2 缓存回归

用户截图中伯斯顿 Prime 已显示灵化攻击模式，却没有灵化之源和适配徽章。核查发现用户配置目录的本地构建是 `localized-text-3`，旧的读取逻辑把“版本哈希不同”当成选择本地数据的充分条件，使旧构建遮盖了新版内置关系。

`src/core/player-dataset.mjs` 先验证当前清单身份，再比较建模版本与全量范围；不兼容时直接读取内置数据，无需加载旧构建的大量溯源内容。本地同结构全量构建继续生效，人工规则仍可使用。`src/core/merge/contract.mjs` 的 `FULL_MODELING_VERSION` 同时供构建与旧版提示使用，避免两处版本判断不一致。内置投影保留来源的 `modelingVersion`，哈希和压缩包完整性校验不变。

新增测试既覆盖空缓存，也模拟 `localized-text-3` 旧缓存启动，通过 Worker 验证伯斯顿 Prime → 伯斯顿灵化之源；UI 回归通过 `--legacy-cache` 注入旧缓存，核对“灵化武器”选项、首屏图片入口和旧缓存原样保留。
