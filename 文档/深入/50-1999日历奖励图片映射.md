## 二、映射档

```js
// src/ui/assets/calendar-1999/reward-art.js
export default {
  // Source: browse.wf/Lotus/Interface/Icons/Rewards/ArcaneGenericRareDoubleIcon128.png, …
  '/Lotus/StoreItems/Types/BoosterPacks/CalendarMajorArtifactPack': 'calendar-1999/rewards/CalendarMajorArtifactPack.png'
};
```

- **键**：世界状态回传的完整奖励 ID，必须以 `/Lotus/` 开头、不含空白。查找前先套用 App 既有的 `storeItemId` 规则（只把开头的 `/Lotus/StoreItems/` 改成 `/Lotus/`），所以 `/Lotus/StoreItems/Types/BoosterPacks/X` 与 `/Lotus/Types/BoosterPacks/X` 是同一笔。两种写法只写一种；同时写两种算**重复映射**，两笔都不生效，避免结果取决于文件顺序。路径中段的 `StoreItems`（例如 `/Lotus/Types/StoreItems/Boosters/…`）是 ID 的一部分，不会改写。
- **值**：相对于 `src/ui/assets/` 的路径，以 `/` 分隔；每段只用 ASCII 字母、数字、点、底线与连字号，且不以点开头，所以不能是绝对路径，也不能含 `..`、`\`、`:`、`?`、`#`。副档名为小写的 `.png`、`.jpg`、`.jpeg` 或 `.webp`。这样路径照写就是安全的网址，不会离开图片根目录。
- **格式**：一笔一行，键与值都写成带引号的字串。验证脚本从原始码读出每个键，才能抓到物件字面量会默默覆盖的重复键。
- **为什么是 JS 模块而不是 JSON**：App 页面的 CSP 是 `connect-src 'none'`。2026-11-06 在 Electron 44 以同一 CSP 实测，`import … with { type: 'json' }` 会被拦截（视为 connect）；JS 模块走 `script-src 'self'`，图片走 `img-src 'self'`，都可载入。App 既有的 `src/data/inline-tokens.generated.mjs` 也是同样原因。
- 映射档在宿主建立时读一次（`createCalendar1999Host`）。规则拒绝的每一笔都交给 `onError(error, 'rewardArt')`（App 中写入 `console.error`）并略过，其他笔照常生效。

## 三、查图顺序（宿主）

画面以 `loadArt({id, libraryId})` 请求；宿主 `src/ui/calendar-1999.js` 依序决定：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | `id` 正规化后有**有效的明确映射**，且浏览器能载入并解码该图档 | `{status:'found', src}`，`src` 为 `src/ui/assets/…` 的 `file://` 网址（打包后在 `app.asar` 内）。不再询问图片服务，即使该奖励有资料库项目 |
| 2 | 没有映射，或映射图档无法读取；且有 `libraryId` 与 App 图片服务 | 以旧卡片同样的请求调用 `api.images`（[47 · 第三节](47-1999日历App能力转接与组装入口.md#三外部能力转接)） |
| 3 | 以上都没有图 | `{status:'missing'}`，画面显示代码绘制的占位图标 |

- 图档是否可读，由宿主以 `Image` 实际载入判断（`readPicture`，可注入；测试以读文件代替）。无法读取时，宿主以 `onError(error, 'loadArt')` 回报可诊断的原因，再走第 2 步。错误物件带 `code: 'ART_FILE_UNREADABLE'`、`rewardId`（映射键）、`path`（映射值）、`src`（实际网址）与 `cause`（原始错误），讯息形如「奖励图片映射的图档无法读取，改用 App 图片服务：<ID> → src/ui/assets/<路径>」。
- 结果按「映射项目 + 资料库目标」保留在本次挂载内：重绘沿用，下次挂载重新判断。两种 ID 写法的映射键相同；图片服务请求失败（reject）时下次重试，与 CAL-07 规则相同。
- 没有映射又没有 `libraryId` 的奖励，不会送出任何图片服务请求。

## 四、取图与资料库跳转分开

- 画面（`calendar-view.js`）对每个奖励都调用一次 `loadArt({ id: reward.id, libraryId })`，由宿主决定图片来源。CAL-08 原本对 `libraryId` 为 `null` 的奖励不请求图片，现已取消这条限制。
- 跳转仍只看 `libraryId`：有资料库目标的奖励才是按钮（`is-linked`、提示「资料库 →」），否则是 `div` 并写「资料库未收录」。有图不会让卡片变成可跳转。
- 奖励原始 ID（卡片 `title` 与 `data-item-id`）、名称、数量与候选语义照原资料呈现，不因图片改变。
- 契约：`CalendarCapabilities.loadArt` 的输入改为 `{id?, libraryId, iconToken?}`（`ports.mjs`）。`id` 是可选栏位，只传 `libraryId` 的旧调用仍有效（宿主照旧只走图片服务）。

## 五、验证流程

`npm run check`（语法检查之后、文本图标检查之前）与 `npm run check:calendar-art` 执行 `scripts/check-calendar-reward-art.mjs`。有任何问题即失败（结束代码 1），并逐笔列出：

| 代码 | 意义 |
|---|---|
| `MAPPING_UNREADABLE` | 映射档无法载入（语法错误等） |
| `INVALID_TABLE` | 默认汇出不是以 ID 为键的物件 |
| `INVALID_ID` | 键不是以 `/Lotus/` 开头、不含空白的完整奖励 ID |
| `INVALID_PATH` | 路径会离开图片根目录，或含不允许的字元 |
| `UNSUPPORTED_TYPE` | 副档名不是小写的 png／jpg／jpeg／webp |
| `DUPLICATE_ID` | 两个键是同一物品的两种写法（两笔都不生效） |
| `DUPLICATE_KEY` | 同一个键写了两次（执行时只会留下最后一笔） |
| `UNCHECKED_FORMAT` | 键不是带引号的字串（例如计算键），无法检查重复 |
| `MISSING_FILE` | 图档不存在 |
| `CASE_MISMATCH` | 路径大小写与实际档名不同：Windows 找得到，打包后的 `app.asar` 找不到 |
| `NOT_PICTURE` | 文件内容不是副档名所说的格式（以档头判断） |

`calendar-1999/rewards/` 内没有任何映射使用的图档，只列为「未被映射使用」，不算失败。前六项与执行时的规则相同（`calendar-1999-art.js`），执行时遇到会略过该笔并回报；其余几项只有文件系统看得到，所以由验证流程负责。

## 六、新增、替换与验证一笔映射

**新增**

1. 准备图档：PNG（建议 128×128、透明背景），或 JPG、WebP。档名照上面的路径规则，建议用 ID 最后一段，例如 `CalendarRivenPack.png`。
2. 放进 `src/ui/assets/calendar-1999/rewards/`。
3. 在 `src/ui/assets/calendar-1999/reward-art.js` 加一行，上方写一行 `// Source: …` 注明图档来源：
   ```js
   '/Lotus/StoreItems/Types/BoosterPacks/CalendarRivenPack': 'calendar-1999/rewards/CalendarRivenPack.png',
   ```
   键可直接从世界状态（`reference.events[].rewardKey`），或从日历来源面板的「完整物品 ID」复制。两种写法都可以，但只写一种。
4. 执行 `npm run check:calendar-art`，应看到「检查通过：N 笔」。
5. 执行 `node --test test/calendar/*.test.mjs`。`reward-art.test.mjs` 会以真实映射档跑一次验证流程，并要求 `rewards/` 内没有未使用的图档。
6. 在 App 中确认：`npm start` → 世界状态 → 快速入口「1999 日历」→ 选该奖励所在的日期，奖励卡右侧应显示图片；或执行 `node scripts/check-calendar-app-ui.mjs`（第 6b 步固定检查 CalendarMajorArtifactPack）。

**替换**：同档名直接覆盖图档即可；改用新档名时，同时改映射值并删除旧图档（否则验证会列出未使用的图档）。重复第 4～6 步。

**移除**：删除映射那一行与图档。该奖励回到 App 图片服务；资料库也没有时显示占位图。

## 十、已知限制与后续

1. **只有一笔映射**：其他日历奖励（赋能包、裂罅 Mod 包、Kuva、Vosfor 等）仍走 App 图片服务；本机没有图库时显示占位图。照第六节逐笔加入即可。
2. **映射一律优先**：即使图库有该物品的图，映射图仍优先，这是 #36 的要求。要改回图库，删除该笔映射。
3. **只在 App 宿主生效**：独立测试页（CAL-09）用假能力，不读映射档；映射规则与顺序由 `composition.test.mjs` 和 App 检查覆盖。
4. **重复键检查依赖写法**：验证脚本从原始码找带引号的键；计算键等其他写法会以 `UNCHECKED_FORMAT` 失败，而不会被放过。
5. **执行时判断可读**：每次挂载对每个（映射项目、资料库目标）载入一次图档；读本机文件，成本很低。图档无法读取的原因只写入主控台，画面不显示诊断讯息。
