# 51 · 1999 日历六人组生日与角色图（CAL-11）

对应 Issue [#37 CAL-11 维护六人组生日与日历角色图](https://github.com/Dreamsunqing/1020-pbex-wfcd-zlk/issues/37)，属于 [#11](https://github.com/Dreamsunqing/1020-pbex-wfcd-zlk/issues/11) 的子任务。承接 [43 · 世界状态转接器](43-1999日历世界状态转接器.md)（`CET_PLOT` 原本一律为 `other`）、[48 · 画面重整](48-1999日历画面重整与应用操作接入.md) 与 [50 · 奖励图片映射](50-1999日历奖励图片映射.md)（图档路径规则与验证流程）。

目标：维护 Arthur、Aoi、Amir、Eleanor、Lettie、Quincy 六人的生日。生日落在当季日历时，日期格显示生日标记；选中该日后，详情显示角色卡（角色图、名称、生日、职位与性格），下方是适合送给该角色的礼物。生日是日历资料，不是事件类型：不改变既有的事件分类、事件日计数、首选日期与快照语义。

## 三、辨识规则（世界状态转接层）

规则只写在 `world-state-source.mjs`。domain、application 与画面只看到转换后的 `birthdays` 与 `notes`，不认识上游栏位。

| 情况 | 结果 |
|---|---|
| 某日有 `CET_PLOT` 事件，`dialogueName` 指明表内角色，且该日正是表内生日 | 采用上游：该角色的生日，`basis: 'upstream'`，`evidence.events` 保存这些事件 |
| 没有事件指明角色；本季 `listedDays` 列出的日期（有无事件皆可）正是表内某角色的生日 | 对照生日表：该角色的生日，`basis: 'table'`，`evidence.listedDay` 记下对照的日期 |
| 列出但不是表内生日的日期（例如第 1、74 天）；或表内生日但本季没列出 | 什么都不加，维持原有显示 |
| 事件指明某角色，但日期与表不同 | **冲突**：该角色在本季不显示生日（两天都不显示）。每笔指明此角色的条目原样保留，并加注 `BIRTHDAY_CONFLICT`（含角色、表定游戏日与日期） |
| `CET_PLOT` 事件没有指明表内角色（缺 `dialogueName`、群组聊天、其他角色、只像名字的档名、`constructor` 等继承名称） | 条目原样保留并加注 `UNRECOGNIZED_PLOT`；日期规则照常适用 |
| 非 `CET_PLOT` 事件带有 `dialogueName` | 不当成生日事件，也不加注 |

- **`dialogueName` 的位置**：宿主的 normalizer 把没有 schema 的栏位放进 `extensions`，所以读取 `event.extensions.dialogueName`；若日后 normalizer 把它提到顶层，先读顶层。`birthdays.test.mjs` 以真实的 `buildWorldView` 跑过一次。
- **空事件的语义不变**：没有事件的列出日期仍然没有条目、`kind: null`、不计入事件日、不作为首选日期。生日来自已核实的生日表与上游列出的日期，不是由「空」推定。
- **evidence** 保存生日表那一笔（含全部来源）与对照的日期或上游事件，都是复本，留在文档中供追溯；角色卡不显示它，也不显示 `basis`。
- 每笔生日另带生日表的 `role`、`personality` 与 `gifts`（复本）。它们描述角色、不描述日期，不影响上面任何规则；表内没有时为 `null` 与空数组。
- `createWorldStateCalendarSource(view, { birthdays })` 可换一份同形的表（测试或维护者核对用），默认为 `HEX_BIRTHDAYS`；不是数组时抛 `TypeError`。

## 四、日历资料与画面模型（契约 1.2.0）

| 位置 | 新增 |
|---|---|
| `CalendarSeason.birthdays?: BirthdayRef[]` | `{ordinal, characterId, name, portraitKey, basis, role?, personality?, gifts?, evidence}`；同一季同一角色至多一笔（`DUPLICATE_BIRTHDAY`）；`role`、`personality` 为字串或 `null` |
| `BirthdayRef.gifts?: GiftRef[]` | `{id, name, note?}`：`id` 为完整物品 ID；格式不对报 `INVALID_GIFT`。只是建议，不记录赠送 |
| `CalendarEntry.notes?: EntryNote[]` | `{code, characterId?, name?, expectedOrdinal?, expectedDate?}`；未知的 `code` 也有效，画面以通用文字显示 |
| `CalendarDay.birthdays: BirthdayRef[]` | domain 按游戏日放到当天，与 `entries` 并列；季度月份以外的生日不显示，也不变成未映射条目 |
| 画面模型 `grid.cells[].birthdays`、`selectedDay.birthdays` | 会话冻结的同一批物件 |

- 生日不改变 `kind`、`eventDays`、首选日期（仍是第一个**事件**日）与 `contextId`。
- 伺服器、季度、轮回与快照：每个新快照仍建立新来源与新会话（ADR-007），所以生日标记与详情永远来自目前的资料；过期、导入、样本快照的提示照旧。
- 能力 `loadPortrait({key}) → Promise<{status:'found', src}|{status:'missing'}>` 是可选的；`validateCalendarCapabilities` 只在存在时检查它是函数（`INVALID_CAPABILITY`）。挂载的能力副本一律提供它：宿主没有时回 `missing`；抛错、reject 或格式不对一律 `missing` 并回报 `onError(error, 'loadPortrait')`；卸载后未完成的请求永不完成。

## 六、角色图映射（宿主）

```js
// src/ui/assets/calendar-1999/portrait-art.js
export default {
  // Source: …
  'hex-lettie': 'calendar-1999/portraits/hex-lettie.png'
};
```

- **键**：生日表的图片资源键，小写 ASCII 字母与数字，以单个连字号连接（`hex-arthur`）。奖励 ID 或其他写法以 `INVALID_KEY` 拒绝。
- **值**：与奖励图片映射相同的路径规则（[50 · 第二节](50-1999日历奖励图片映射.md#二映射档)），图档放在 `src/ui/assets/calendar-1999/portraits/`。
- **查图**：宿主只查这份映射；有有效且浏览器能解码的图档时回 `found`，否则 `missing`。角色图不经 App 图片服务，也不与奖励图片共用键。每次挂载每个键只读一次。
- **诊断**：映射档中被拒绝的笔数以 `onError(error, 'portraitArt')` 回报；图档无法读取以 `onError(error, 'loadPortrait')` 回报，错误带 `code: 'PORTRAIT_FILE_UNREADABLE'`、`portraitKey`、`path`、`src` 与 `cause`。
- **验证**：`npm run check:calendar-art`（`npm run check` 也会跑）对角色图映射执行与奖励图片相同的检查（`INVALID_TABLE`、`INVALID_PATH`、`UNSUPPORTED_TYPE`、`DUPLICATE_KEY`、`UNCHECKED_FORMAT`、`MISSING_FILE`、`CASE_MISMATCH`、`NOT_PICTURE`），另加 `INVALID_KEY` 与 `UNKNOWN_PORTRAIT_KEY`（生日表没有角色使用的键）。生日表中尚无角色图的角色逐一列为「尚无角色图，日历显示占位图」，不算失败。

## 七、维护方式

### 核对生日

1. 以游戏内 KIM 角色资料或游戏内 1999 日历为准；转录来源（wiki）只作为查阅途径。
2. 修改 `hex-birthdays.mjs` 该笔的 `month`、`day`，并更新 `sources` 的 `quote` 与 `checkedAt`。游戏日由 domain 换算，不必手改。
3. 执行 `node --test test/calendar/*.test.mjs`。`birthdays.test.mjs` 第一项会列出全部六人的日期与游戏日，需要一起更新；测试资料 `birthdays.json` 若受影响，以第九节的情境重新确认。

### 新增或替换角色图

1. 准备图档：PNG（建议正方形、透明或纯色背景），或 JPG、WebP。档名用图片资源键，例如 `hex-lettie.png`。
2. 放进 `src/ui/assets/calendar-1999/portraits/`。
3. 在 `portrait-art.js` 加一行，上方以 `// Source: …` 注明来源（例如官方 `ExportManifest` 的贴图路径）。
4. 执行 `npm run check:calendar-art`，该角色应从「尚无角色图」清单消失。
5. 在 App 中确认：`npm start` → 世界状态 → 快速入口「1999 日历」→ 2 月 → 14 日；或执行 `node scripts/check-calendar-app-ui.mjs`（第 6c 步：映射有 `hex-lettie` 时要求图档实际载入）。

替换时同档名直接覆盖；改档名时同时改映射值并删除旧图档（否则验证会列出未使用的图档）。

候选图源（官方 `ExportManifest`，本机 `世界状态上游/official-public-export/manifests/en/ExportManifest.json` 已列出）：`/Lotus/Types/StoreItems/AvatarImages/AvatarImagePixel<Name>` 的像素浮印 `/Lotus/Interface/Icons/Player/<Name>PixelGlyph.png`，六人都有；另有 `<Name>AccoladeGlyph`（荣誉浮印）。

### 修改职位、性格或礼物

1. 改 `hex-birthdays.mjs` 该笔的 `role`、`personality` 或 `gift`，并以自己的文字书写；礼物名称以官方 `dict.zh` 为准。
2. `birthdays.test.mjs` 会检查每件礼物都是官方导出中的物品、中文名与 `dict.zh` 一致，以及职位末尾的原型战甲名称。
3. 礼物图片：把图档放进 `src/ui/assets/calendar-1999/rewards/`，在奖励图片映射 `reward-art.js` 以礼物的完整物品 ID 加一行（规则同 [50 · 第六节](50-1999日历奖励图片映射.md#六新增替换与验证一笔映射)）。官方图示路径为 `/Lotus/Interface/Icons/StoreIcons/Resources/1999Wf/HexDogTag<Name>.png`。

### 处理来源冲突

画面出现「生日资料冲突」时：

1. 打开该条目的「资料来源与原始事件」，确认上游事件的 `dialogueName` 与日期。
2. 以游戏内 KIM 或日历核对正确的生日。
3. 表错了：依「核对生日」修改并补上来源。上游的聊天室档名换了：在该角色的 `dialogues` 加上新档名（逐字）。上游本身错：不改表，冲突会持续显示原事件，直到上游修正。
4. 「未识别的剧情事件」不会挡住生日表对照；若确认是新角色或新聊天室，再决定是否加入表内。

### 新增角色

在 `HEX_BIRTHDAYS` 加一笔（稳定 ID、显示名称、月日、图片资源键、聊天室档名、来源），并视需要在 `portrait-art.js` 加图。验证脚本会对新键列出「尚无角色图」。

## 十一、已知限制与后续

1. **角色图档目前收录碧**。`hex-aoi.png` 采用 Warframe Public Export 的 Aoi Accolade Glyph，其他五位角色显示占位图。App 检查脚本第 6c 步使用冬季样本验证莱蒂的占位图，加入莱蒂的图档后，该步骤会要求图片成功解码。
2. **`dialogueName` 尚未以实际上游样本核对**：本机两份离线样本没有 `CET_PLOT` 事件。栏位名称依社群解析器的惯例；若实际栏位不同，上游规则不会生效，但会回到生日表对照并对该事件加注「未识别」，不会显示错的角色。
3. **只有六人组**：圆桌成员（例如 Kaya 1 月 1 日、Velimir）不在表内，相关列出日期维持原样。需要时依第七节新增。
4. **显示名称只有简体中文**，与 App 一致。
5. **冲突只在原事件上提示**：表定日期若是没有事件的列出日期，该日不显示冲突说明（说明写在上游事件那一天）。
6. **角色卡不显示对照依据与来源**：依需求移除。要查某个生日是依上游事件还是依生日表对照，看文档中的 `basis` 与 `evidence`（浏览器检查读 `data-birthday-basis`）。
7. **职位与性格是摘要**：依 wiki 角色档案改写，非游戏内原文；剧情推进后的人物变化未纳入。
8. **礼物是主题对应的建议**：游戏没有生日送礼机制，六人组宝物实际用途是交给莱蒂换取声望。超级比特披萨、氩汉堡套餐不对应特定角色，未列入。礼物尚无图档，显示奖励占位图示。
